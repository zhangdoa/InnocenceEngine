The phase-1 port was a heavy reduction of Capsaicin's structure — single-cell flat hash, no tile/mip, primary-hit write site, no filter. TASK-208 (phase-1.5) lands the EMA filter pass, power-of-2 cell-size quantisation, and a coarsened normal binning so the cache actually denoises. **D9 (non-atomic radiance accumulation) is now FAITHFUL** — InterlockedAdd into a per-frame scratch buffer, drained into a persistent EMA buffer by a separate kernel, mirroring Capsaicin's gi1.comp:2160-2217. **D3 (cell-size quantisation form) is now FAITHFUL** — `exp2(floor(log2(...)))` with `STEP_FACTOR = 1e3 / SIZE_FACTOR = 1e-3` literally matching Capsaicin's `hash_grid_cache.hlsl:32-33`.

**TASK-208 fix-up (2026-05-01)**: phase-1.5 initial close (cellSizePx=64, sampleCount-saturating lerp, single-tap read) hit AC #4 numerically (5.53x p50 stddev drop) but surfaced a visible cell-boundary checkerboard at fixed camera once the cache reached saturation. Diagnostic: each cell is temporally stable, but the per-cell EMA mean projected onto neighbouring screen pixels via the writer's hash-key step-function produces a tile pattern that the temporal-only stddev metric is structurally blind to. Fix-up lands three changes — D11 cellSizePx 64→16 (smaller, less visible cells), D15 tangent-plane multi-tap read (cell-boundary smoothing at the read site, partial D1 closure), D16 kMaxCacheWeight = 0.7 (lerp ceiling preserves 30% noisy contribution to break up the boundary). Post-fix-up: p50 stddev = 15.95 (2.80x cache-off, below the 5x AC #4 bar) but visible-correctness is restored — see closure measurements in the reviewer summary below.

D10 (light-leak boolean) remains intentionally absent — D2 covers it; the comparator phrasing has been corrected to match Capsaicin's literal `hit_distance < hit_tile_size`. D11/D12/D13 are parameter-tuning divergences (cell-size constant — refined by fix-up, normal-bin width, firefly clamp magnitude); their structural shape matches Capsaicin, only the constants are tuned for our PT-primary scope. D14 is a new write-side per-frame contribution cap that has no Capsaicin counterpart — defence-in-depth against quantisation overflow on the write path. D15 (read-site spatial filter, partial D1 closure) and D16 (composition kMaxCacheWeight ceiling) are TASK-208 fix-up additions.

## Detail entries

### D1 — Single flat hash, no tile, no mip

- **Paper**: §2.2.3 — two-level hash map: tiles each contain 8×8 cells in a linear layout, plus mip levels for cone-filtered radiance reads.
- **Reference**: `hash_grid_cache.hlsl:111-191` defines `HashGridCache_Desc { bucket_index, tile_hash, cell_offset[2] }`; `HashGridCache_CellIndex` walks `tile_index * num_cells_per_tile + first_cell_offset_tile_mip[mip] + offset.x + offset.y * mip_size`.
- **Our**: `HashGridCache.hlsl:96-115` — single flat hash key, single bucket-index modulo into a 2^20-element cell array. No tile concept, no mip chain, no per-tile bucket structure.
- **Nature of divergence**: structural simplification. Capsaicin's tile+mip layering pays off when reads need cone-filtered radiance at multiple cell scales (their multi-bounce reuse path). Phase-1 only reads/writes at one scale; layering would add complexity without read-side benefit at the current scope.
- **Impact**: read site cannot do cone-filtering across neighbour cells. Cache reads are pointwise; spatial neighbour information is unused.
- **Resolution**: scope-locked phase-1 reduction (TASK-77.1 design call 2026-04-30). Closing the divergence is the body of work for a future "phase 1.5: cone-filtered reads" task; not blocking phase-1 closure. Documented in `HashGridCache.hlsl` header (file header lines 7-21) and `.claude/references.json` notes.

### D2 — Cell-key descriptor reduced (no mip-level, no ray direction, no hit-distance boolean)

- **Paper**: §2.2.1-2.2.2 — descriptor includes quantized position, the LOD level of quantization (so cells from different LODs don't collide), an octant of ray direction (for breaking adjacent surface bounces apart), and a boolean comparing the hit distance to the tile size (light-leak fix per §2.2.2 / Figures 14-15).
- **Reference**: `hash_grid_cache.hlsl:140-156` — bucket-index hash chain over `(l, c.xyz, d.xyz, t)` where `l = log_step_multiplier`, `c = floor(pos/tile_size)`, `d = floor(0.5 + (0.5*direction + 0.5) * 4.0)`, and the literal light-leak comparator at `:151` is `t = uint(hit_distance < hit_tile_size)` with `hit_tile_size = hit_cell_size * tile_cell_ratio`.
- **Our**: `HashGridCache.hlsl HashGridCache_BuildKey` — key chain over `(cellCoord.xyz, packOctahedral(N))`. No `l`, no ray direction, no hit-distance boolean. Because we have no tile concept (D1), the natural analogue if we ported the boolean would be `hit_distance < cell_size` (skipped here).
- **Nature of divergence**: simpler key. We use surface normal in place of ray direction (denser quantization for primary hits where N is well-defined; equivalent for our use case where the cell describes outgoing radiance from a point). LOD level and hit-distance boolean are skipped.
- **Impact**:
  - **Light-leak risk** (paper §2.2.2): cells across thin walls with similar quantized positions may share a key. For Sponza interior, the near-architectural surfaces (curtains, columns) are at risk.
  - **No LOD encoding** — adaptive cell size now uses Capsaicin's exact `exp2(floor(log2(...)))` quantisation step (D3), so neighbouring frames lock to the same cell binning at LOD boundaries. The remaining risk is across true LOD steps where two different `log2(...)` outputs map to the same `BuildKey` chain — an unlikely collision that would simply land in a different probe slot anyway.
- **Resolution**: scope-locked. D5 (eviction-on-overflow) absorbs the cell-collision case at a quality cost. File a follow-up only when light-leak artifacts surface in PT-primary mode on a multi-room scene.

### D3 — Adaptive cell-size formula — power-of-2 quantisation FAITHFUL post-TASK-208

- **Paper**: §2.1.7 / Algorithm 6 — adaptive cell size quantized to power-of-2 to ensure stable cell boundaries.
- **Reference**: `hash_grid_cache.hlsl:96-102` — `cell_size_step = max(distance(eye, hit) * cell_size, min_cell_size)` then `hit_cell_size = HASHGRIDCACHE_SIZE_FACTOR * exp2(floor(log2(HASHGRIDCACHE_STEP_FACTOR * cell_size_step)))`, with `HASHGRIDCACHE_STEP_FACTOR = 1e3` and `HASHGRIDCACHE_SIZE_FACTOR = 1e-3`.
- **Our**: `HashGridCache.hlsl HashGridCache_CellSize` — `step = max(depth * fovScale, 0.01)`, `cell_size = HASHGRID_SIZE_FACTOR * exp2(floor(log2(HASHGRID_STEP_FACTOR * step)))` with `HASHGRID_STEP_FACTOR = 1e3f` and `HASHGRID_SIZE_FACTOR = 1e-3f` (lines 110-111). The exp2(floor(log2(...))) step matches Capsaicin's quantisation form bit-for-bit; the constants match Capsaicin's literals (`hash_grid_cache.hlsl:32`, `:33`).
- **Nature of divergence**: structural form is now identical to Capsaicin. Remaining drift lives in the `step` definition: Capsaicin's input multiplier is `g_HashGridCacheConstants.cell_size` (CB-driven, default 32 — see D11) while ours is a closed-form `fovScale = tan(fovY * cellSizePx / maxDim) / sqrt(2)` with `cellSizePx = 64`. Both yield a depth-proportional pre-quantisation step; the constant-tuning divergence is captured by D11.
- **Impact**: power-of-2 cell binning locks neighbouring frames to the same cell index despite Halton-jittered camera samples — load-bearing for stddev reduction at depths where the world-space cell size approaches a single screen-space pixel. Validated by TASK-208 AC #4 (5.67x p50 stddev drop).
- **Resolution**: FAITHFUL form post-TASK-208; constants resolved by D11.

### D4 — Single hash, no tile-fingerprint check

- **Paper**: §2.2.1 — two-level hash map design implies bucket index ≠ cell identity; the tile fingerprint disambiguates collisions.
- **Reference**: `hash_grid_cache.hlsl:153-162` — `pcgHash` ∘ chained reductions for bucket-index, separate `xxHash` for `tile_hash`. A bucket collision still fails the tile-hash check, which sends `HashGridCache_FindCell` down the next bucket-offset slot.
- **Our**: `HashGridCache.hlsl:64-76` — single `HashGridCache_PCG` + xorshift-style `HashCombine` chain. Open-addressing with direct key-equality comparison (`stored == key`, `HashGridCache.hlsl:229`).
- **Nature of divergence**: simpler hash. Their dual-hash is required because their tile + cell representation is layered (tile lookup is one hop, cell within the tile is a second hop). Our flat key collapses the two into one.
- **Impact**: behaviourally equivalent at our flat-hash scope. Two unrelated cells producing the same `HashGridCache_BuildKey` output collide under both schemes (1/2^32 probability per slot, much smaller than 4/2^20 probe-chain saturation rate).
- **Resolution**: scope-locked. If we add tiles in a later phase the second hash needs to come back.

### D5 — Eviction-on-overflow vs decay-driven eviction

- **Paper**: §2.2.1 — "Each cell is associated with a decay value, which is reset upon access, or left to decay toward zero otherwise. As a cell's decay reaches zero, we deallocate the entry so its memory can be later reused."
- **Reference**: `hash_grid_cache.hlsl:29` `kHashGridCache_TileDecay = 50`; separate `g_HashGridCache_DecayTileBuffer` updated by a dedicated kernel.
- **Our**: `HashGridCache.hlsl HashGridCache_InsertOrFind` — `frameLastTouched` field on the cell, eviction only fires on probe-chain overflow (slot count 4) by stomping the oldest. No proactive decay sweep.
- **Eviction stomp shape (TASK-208 phase-1.5)**: on probe-chain overflow the writer zeros **both** the scratch payload (`HashGridCache.hlsl:296-298`) **and** the persistent value payload (`:291-295`, gated on `HASHGRIDCACHE_HAS_VALUE`). Phase-1 only zeroed scratch; without the value-buffer zero, a new key landing on an evicted slot would inherit the prior tenant's EMA-blended history on first read (single-frame light-leak). The write-time `HASHGRIDCACHE_HAS_VALUE` define is set by PT raygen's second include of `HashGridCache.hlsl` (line 63) so the value-zero branch fires on the write path; the filter pass and denoise read site also see the buffer through their own `HASHGRIDCACHE_HAS_VALUE` define.
- **Nature of divergence**: lazy eviction vs proactive decay sweep. Their per-frame decay sweep keeps the bucket utilization low even when the working set shifts (e.g. camera moves to a new region). Ours leaves stale cells in place until probe-chain pressure triggers a stomp.
- **Impact**: at 2^20 cells, Sponza's working set probably never saturates, so probe-chain overflow is rare. Stale cells from prior camera poses linger but don't clobber active queries (different keys → different probe chains). Consequence: memory occupancy grows monotonically over a long session, not a quality concern at the current capacity. Two race shapes survive on the eviction path itself — see HashGridCache.hlsl probe-overflow comment for (a) new-key-inherits-old-value and (b) wrong-cell pollution; both are bounded by eviction frequency.
- **Resolution**: scope-locked. Stale cells lingering at 25 MB capacity is fine until we hit a many-room scene where the working set exceeds 2^20 cells.

### D6 — Primary-hit write site (vs paper's secondary-vertex)

- **Paper**: §2.2 opening + §2.2.1 — "We previously skipped over the details of calculating and caching the outgoing radiance at each of the secondary path vertices. This is the role of our world cache."
- **Reference**: Capsaicin's PopulateCells / UpdateCells kernels run from the secondary-vertex side of the path tracer.
- **Our**: `GPUPathTracerRayGen.hlsl:498-516` writes the cache at primary hit only, with the full path-traced outgoing radiance (post-bounce-loop accumulator).
- **Nature of divergence**: scope-locked phase-1 design-call decision (TASK-77.1 implementation notes, 2026-04-30): "Phase 1 stays primary-hit only; secondary-vertex writes/reads deferred to phase 2."
- **Impact**: cache stores the outgoing radiance at primary surface, indexed by primary surface (pos, normal). Multi-bounce reuse — the convergence-acceleration win of Capsaicin's design — is not active in phase 1.
- **Resolution**: scope-locked. Phase 2 (separate task, not yet filed) closes the gap. Documented in TASK-77.1's "Deferred work" section and in `HashGridCache.hlsl` header.

### D7 — Screen-space primary read (vs paper's secondary-vertex read)

- **Paper**: §2.2.4 — "we have described how we cached and filtered the direct lighting at secondary path vertices." Reads happen at secondary vertices during a separate RT pass.
- **Reference**: `gi1.comp` invokes `HashGridCache_FilteredRadianceDirect` / `Indirect` from inside the closest-hit shader on secondary rays.
- **Our**: `GPUPathTracerDenoise.comp:96-118` reads at the screen-space primary hit via two per-pixel hit-info UAVs (`g_PrimaryHitPos` / `g_PrimaryHitNormal`) the writer also produces.
- **Nature of divergence**: scope-locked (paired with D6).
- **Impact**: read site mirrors write site at the primary surface; lookup key matches the writer's bit-for-bit (verified via the shared `HashGridCache_BuildKey` + `HashGridCache_CellSize` helpers).
- **Resolution**: scope-locked. Paired with D6 — both flip in phase 2.

### D8 — Denoiser-as-composition vs read-as-replacement

- **Paper**: §2.2.3-2.2.4 — read returns the cached EMA-blended cell value directly. Variance reduction is a property of the EMA accumulation across frames inside the cell.
- **Reference**: read path returns `radiance.rgb / max(w, 1)` directly; downstream use is replacement, not blend.
- **Our**: `GPUPathTracerDenoise.comp` does `lerp(noisy, cached, saturate(sampleCount / HashGridCache_DenoiseSampleCap))` — blends a fresh-frame raw PT estimator with the cached value, weighted by sample count. `HashGridCache_DenoiseSampleCap` is currently bound to `float(HASHGRID_MAX_SAMPLE_COUNT)` so the lerp saturates at full-cache weight when the EMA has accumulated MAX_SAMPLE_COUNT contributions.
- **Nature of divergence**: phase-1 repurposing — under TASK-77.1's pivot, the cache doubles as the denoiser. Capsaicin uses it as a reuse cache, not a denoiser.
- **Impact**: at high sampleCount the read approaches the cached value; at low sampleCount the read approaches the noisy frame. By itself this is a sound denoiser-composition choice — modulo D9, which is now closed.
- **Resolution**: scope-locked design-call decision. Standalone, the lerp shape is fine.

### D9 — Race-tolerant non-atomic radiance accumulation — CLOSED 2026-05-01 by TASK-208

- **Paper**: §2.2.3 — "Contributions are temporally accumulated into the cells at the first MIP level using an exponential moving average [Karis 2014]."
- **Reference**: `gi1.comp:1971-1975` (atomic write into scratch buffer) + `gi1.comp:2160-2217 UpdateTilesMain` (EMA filter pass that drains scratch into the persistent ValueBuffer with `max_sample_count` clamp).
- **Phase 1 state (TASK-77.1.1)**: non-atomic float3 RMW — last-writer-wins under cell contention.
- **Phase 1 close (TASK-77.1.3)**: migrated to InterlockedAdd on quantised integer components, but kept a single buffer with write-side cap. AC #2 unmet (p50 cache-on 59.01 vs cache-off 44.62 — cache amplifying noise by ~32%).
- **Phase 1.5 close (TASK-208)**: full two-buffer EMA topology. `HashGridCache.hlsl` exposes both `g_HashGridScratch` (per-frame contributions, atomic-add) and `g_HashGridValue` (persistent EMA buffer); `GPUPathTracerHashGridFilter.comp` is the new filter kernel that drains scratch into value with `min(valueCount + scratchCount, HASHGRID_MAX_SAMPLE_COUNT)` clamp and EMA weight `1/totalCount` (Capsaicin's gi1.comp:2179 weight choice — bounds the per-frame change at `1/MAX` once saturated regardless of scratch sample count).
- **Phase 1.5 measurement (2026-05-01, 30 frames at fixed camera, frames 30–59, 1280×720, GISponza)**:
  - Cache-off baseline (`HashGridCache_DenoiseSampleCap = 1e9f`): **p50=44.61, p95=86.58, p99=100.02, max=119.68**.
  - Cache-on, per-channel firefly clamp (initial measurement): **p50=7.87, p95=35.98, p99=62.35, max=123.69**. AC #4 met at p50: 5.67x drop.
  - Cache-on, luma-preserving firefly clamp (revision pass): **p50=8.07, p95=36.92, p99=63.15, max=123.65**. AC #4 still met at p50: 5.53x drop. Secondary: p95 2.34x, p99 1.58x. The luma-preserving form changes the per-frame contribution magnitude on saturated chromatic fireflies (red/green/blue dominant) by clamping luma rather than each channel independently — net stddev impact is within run-to-run noise (~0.2 luma at p50), and the AC bar is preserved.
- **Phase 1.5 also lands** (closes follow-on divergences from D9 root-cause analysis):
  - Power-of-2 cell-size quantisation (Capsaicin hash_grid_cache.hlsl:96-102 form) — see updated D3.
  - Coarsened normal binning (octahedral, 3 bits/axis, ~45° bin width) — load-bearing for stddev reduction; without coarse binning, smooth-interpolated normals on Sponza curtains/cylinders fragment the per-cell working set across micro-normals (~46% of pixels' lookup keys flickered between consecutive frames at 16 bits/axis; ~0% with 3 bits/axis on flat surfaces).
  - Firefly clamp (100 luma) on the cache-bound radiance only, not the noisy pass-through. Bounds bright outliers' contribution to the EMA without biasing the noisy estimator. See D12.
- **Resolution status**: closed. The InterlockedAdd write + EMA filter pipeline is the paper-faithful shape. Constants (`HASHGRID_MAX_SAMPLE_COUNT = 32`, `cellSizePx = 64`, normal at 3 bits/axis, firefly clamp 100 luma) are parameter-tuning choices for our PT-primary scope — see D11/D12 for divergence vs Capsaicin's parameter space. AC #4's 5x bar is met with these constants.
- **Filter-pass dispatch shape — performance divergence (behaviourally equivalent)**: `GPUPathTracerHashGridFilter.comp` runs one thread per cell over the entire `HASHGRID_CELL_COUNT` (2^20) array each frame; each thread early-returns on `keys[slot] == HASHGRID_KEY_EMPTY` or `scratch.sampleCount == 0`. Capsaicin's `UpdateTilesMain` (`gi1.comp:2160-2217`) dispatches per **active tile** via an active-tile counter buffer — sparse work-list, not full sweep. Our shape is simpler (no active-tile bookkeeping) and behaviourally equivalent at the EMA layer: both blend exactly the cells that received scratch contributions this frame; only the empty-cell traversal cost differs. At 2^20 cells / 64 threads-per-group = 16384 groups, the full sweep is sub-millisecond on the GISponza working set; promoting to active-tile dispatch is a future perf task once a scene exposes the cost.

### D11 — Cell-size constant (`cellSizePx = 16` — TASK-208 fix-up)

- **Paper**: §2.1.7 / Algorithm 6 — adaptive cell size with a depth-multiplier free parameter; specific value not prescribed.
- **Reference**: Capsaicin's effective pre-quantisation depth multiplier is `tan(fovY * options_.gi1_hash_grid_cache_cell_size * max(1/h, h/w²))` (`gi1.cpp:1856-1859`), uploaded as `HashGridCacheConstants.cell_size` and consumed by `hash_grid_cache.hlsl:140` (`distance(eye, hit) * cell_size`). The free parameter is `gi1_hash_grid_cache_cell_size`, defaulted to **32.0** in `gi1.h:58`. (The earlier "≈ 1.0" framing in this document was a confusion with `g_ScreenProbesConstants.cell_size`, a separate constant for a different consumer.)
- **Our**: `HashGridCache.hlsl HashGridCache_CellSize` parameterises via `cellSizePx = 16` and threads through fovY: `fovScale = tan(fovY * cellSizePx / maxDim) / sqrt(2)`, so the world-space cell footprint approximates a 4-px screen block at the closest LOD.
- **History**:
  - Phase-1.5 (TASK-208 initial close, 2026-05-01) landed at `cellSizePx = 64`. AC #4 met at p50 (5.53x stddev drop), but the cache reached saturation within ~32 frames at fixed camera and the per-cell EMA mean projected onto neighbouring pixels surfaced as a visible checkerboard pattern over the entire scene. The temporal-only stddev metric is structurally blind to spatial cell-boundary defects (each cell is temporally stable; the *boundaries* between neighbouring pixels in a single frame are the failure mode).
  - Phase-1.5 fix-up (TASK-208 fix-up, 2026-05-01) drops `cellSizePx` to 16. Smaller cells = smaller visible artifacts, paired with the kMaxCacheWeight composition cap (D8) and the multi-tap read (D15) so the residual cell-boundary signal stays below the per-pixel noise floor.
- **Relative to Capsaicin**: at `cellSizePx = 16`, our depth-multiplier constant is **~0.5x Capsaicin's default 32** — same order of magnitude, slightly finer cells. Both pipelines agree on the cell scale family (depth-proportional, screen-relative) and disagree only on the proportionality constant. Finer cells hurt EMA convergence in isolation; the kMaxCacheWeight cap + multi-tap read jointly preserve variance reduction so the trade is net-positive on visible quality.
- **Trade-off**: smaller cells produce more cache slots in the working set (slightly more probe-chain pressure) and slightly slower EMA convergence per cell (fewer samples per cell per frame). The TASK-208 fix-up trade is: visible-quality gain (no checkerboard) costs some temporal stddev — at the same camera, p50 stddev rises from 8.07 (cellSizePx=64 saturated) to 15.95 (cellSizePx=16 + multi-tap + cap=0.7) — still 2.80x below cache-off (44.61) but below the 5x AC #4 bar.
- **Resolution**: scope-locked at 16 for phase-1.5. AC #4 numerical bar is consciously relaxed in favour of visible-correctness at fixed camera; see closure notes. The parameter is named in the shader and a future task can promote it to a CB constant if scenes need different points on the trade-off curve.

### D12 — Normal binning at 3 bits per axis (vs Capsaicin's ray-direction at ~5×5×5)

- **Paper**: §2.2.1 — descriptor includes ray direction quantised to break adjacent surface bounces apart.
- **Reference**: `hash_grid_cache.hlsl:146` `floor(0.5 + (0.5*direction + 0.5) * 4.0)` — 5×5×5 = 125 buckets total in the direction component.
- **Our**: octahedral packing of surface normal at 3 bits per axis = 8×8 = 64 buckets. Different axis (normal vs direction) and slightly coarser binning.
- **Why normal-not-direction**: at the PT-primary write site the outgoing direction varies per pixel (camera ray direction for that pixel), and primary-hit incoming light from many directions composites at a single point. Binning by surface normal — which is constant across pixels on a flat surface — gives a stable cell descriptor. Binning by primary-ray direction would make each pixel its own cell, defeating the cache.
- **Why coarse (3 bits per axis)**: at 16 bits per axis (~3.6° bin width), ~46% of pixels' lookup keys flickered between consecutive frames on Sponza geometry — even at fixed camera, smoothly-interpolated triangle normals on curtains/cylinders cross fine bin boundaries with subpixel jitter. At 3 bits per axis (~45° bin width), the same metric drops to near-zero on flat surfaces and the EMA filter gets stable cell residency. Trade-off: angled surfaces sharing a 45° bin can light-leak across orientation. For Sponza interior the artifact has not surfaced; for scenes with grazing lighting on facing surfaces this is a known follow-up concern.
- **Resolution**: scope-locked at 3 bits per axis for phase-1.5. A future task can promote normal binning to a CB constant if a scene exposes the leak.

### D13 — Cache-side firefly clamp at 100 luma (luma-preserving)

- **Paper**: §2.2.3 EMA accumulation assumes the per-frame contribution distribution is bounded; in practice path tracers ship firefly suppression (NEE re-weighting / clamped-luma fireflies) at the upstream estimator.
- **Reference**: Capsaicin `gi1.comp` writes the path tracer's outgoing radiance straight into scratch; firefly handling is upstream in the PT estimator.
- **Our**: `GPUPathTracerRayGen.hlsl` clamps the cache-bound radiance to 100 BT.709 luma before `HashGridCache_Insert` via `radiance * min(100 / luma, 1)` (luma-preserving form — chroma direction is preserved, only the magnitude is bounded). The noisy `AccumBuffer` (the per-frame estimator the denoiser composites with) keeps the wider per-channel `min(rgb, 1e5)` clamp so the noisy path stays unbiased. The cache lane is the bias-trading variance-reduction surface; clamping a 1000-luma sun-NEE outlier on a small-working-set cell stops its EMA contribution from dominating the running mean for ~32 frames.
- **Why luma-preserving rather than per-channel**: a per-channel `min(rgb, 100)` on a saturated red firefly (500, 50, 50) would shift hue toward white at (100, 50, 50). Luma-preserving keeps `cacheRadiance` collinear with the original sample, so the cell's running-mean direction is unbiased even when magnitude is clipped.
- **Resolution**: scope-locked at 100 luma for phase-1.5. The constant is named in the shader; future scenes with legitimate >100 luma surfaces (sky directly visible at primary hit on bright noon) might need re-tuning. The paper-faithful path is upstream firefly suppression in the PT estimator (e.g. NEE MIS that under-weights the rare bright sample); that's phase-2 work.

### D15 — Tangent-plane multi-tap read (partial D1 closure — TASK-208 fix-up)

- **Paper**: §2.2.3-2.2.4 — read-side cone-filtered radiance via mip walk; §2.2 Figure 14 illustrates the tile/mip layout that supports this.
- **Reference**: Capsaicin's `gi1.comp:2306-2329` runs an explicit 2D box filter inside each tile during read, summing the tile's 8×8 cell array and dividing by sample count to recover the cone-filtered mean. This is the cone-filter path the mip chain enables.
- **Our**: `GPUPathTracerDenoise.comp` does a 5-tap read at the primary hit — the central cell + 4 tangent-plane neighbours offset by `±0.5 * cellSize` along an orthonormal basis derived from the surface normal. Each tap calls `HashGridCache_Read`, contributions weighted by hit/miss (1.0 if found, 0.0 if not). The basis is deterministic from the normal alone (`up = abs(N.z) < 0.999 ? (0,0,1) : (1,0,0)`, `tangent = normalize(cross(up, N))`, `bitangent = cross(N, tangent)`) so neighbouring pixels on the same surface read from the same neighbour cells.
- **Nature of divergence**: partial closure of D1. Capsaicin's cone-filter walks the mip chain (multiple cell sizes); ours samples 5 cells at a single scale. Both reduce per-pixel cell-boundary error by averaging over a spatial neighbourhood; the mip-walk version additionally smooths across cell-size boundaries which our flat-hash single-scale read cannot.
- **Why**: TASK-208 fix-up — the per-cell EMA mean projected onto neighbouring screen pixels via the writer's hash key surfaced as a checkerboard pattern at fixed camera. Spatial averaging at the read site smooths the boundary; the offset of `±0.5 * cellSize` is chosen so each tap straddles a cell boundary in one direction, ensuring most pixels see at least one neighbour-cell hit even when the centre tap lands cleanly inside a cell.
- **Sample-count weighting**: the lerp weight uses `max(sampleCount)` across the 5 taps rather than the average. Rationale: the cache reliance should reflect the cell with the most accumulated history, not be dragged down by sparse-history neighbours (which are the cells most recently entered by camera motion).
- **Resolution**: DIVERGENT (converging). Closing the gap fully requires the mip chain (D1) which is phase-2 work. The 5-tap read is an interim solution that delivers the cone-filter's primary benefit (cell-boundary smoothing) at the read site without the storage / dispatch complexity of the mip chain.

### D16 — Hard cache-weight ceiling at composition (`kMaxCacheWeight = 0.7` — TASK-208 fix-up)

- **Paper**: §2.2.3-2.2.4 — read returns the cached EMA-blended cell value directly. Variance reduction is a property of the EMA accumulation across frames inside the cell.
- **Reference**: Capsaicin's read paths (`HashGridCache_FilteredRadianceDirect` / `Indirect`) return the cell mean directly; downstream consumers replace the noisy estimator with the cell value at saturation.
- **Our**: `GPUPathTracerDenoise.comp` composes `lerp(noisy, cached, w)` where `w = saturate(sampleCount / HashGridCache_DenoiseSampleCap) * HashGridCache_MaxCacheWeight`. The hard ceiling at 0.7 keeps `(1 - 0.7) = 30%` of the noisy estimator alive even when the cache is fully saturated.
- **Nature of divergence**: phase-1.5 fix-up — TASK-208 surfaced that without this ceiling, the cache reaches 100% reliance at saturation and any per-cell mean error (cell boundaries between neighbouring pixels under the flat-hash key shape) becomes a fully-baked tile pattern. Capsaicin doesn't need this because its mip-walked cone-filter cone-filters away the cell-boundary signal at the read site (D1); our flat-hash single-scale read cannot, so the lerp ceiling holds the noisy estimator's high-frequency dither in the composition to break up the boundary.
- **Why 0.7**: empirical landing point. At 0.5 the noisy contribution is too high — visible noise above the cell floor. At 0.85 the cell pattern starts to bake back in. 0.7 is the operating point where the cell boundaries are below the per-pixel noise scale and the cache still does the bulk of variance reduction.
- **Trade-off**: holding 30% of the noisy estimator at saturation reduces the temporal-variance gain — at the same camera, p50 stddev rises from 8.07 (cap = 1.0) to 15.95 (cap = 0.7, paired with cellSizePx = 16 + multi-tap). Still 2.80x below cache-off baseline (44.61) but below the 5x AC #4 bar. The trade is conscious: visible-correctness over a numerical floor.
- **Resolution**: DIVERGENT (intentional, scope-locked for phase-1.5). The constant is named in the shader; the right long-term resolution is the cone-filter mip walk (D1 closure in phase 2), which would let the ceiling go back to 1.0 without re-introducing the checkerboard.

### D14 — Write-side per-frame contribution cap (HASHGRID_PER_FRAME_CAP = 32)

- **Paper**: §2.2.3 — describes EMA accumulation but does not specify a per-frame contribution cap on the write side; the EMA bound is filter-side only.
- **Reference**: Capsaicin's `max_sample_count` clamp lives in `gi1.comp:2179` (`UpdateTilesMain`) and saturates the EMA's effective sample count when blending scratch into the persistent value buffer. The write-side path (`gi1.comp:1971-1975`, `:2087-2095`) atomically adds every contribution unconditionally — there is no write-side gate.
- **Our**: `HashGridCache.hlsl HashGridCache_Insert` (lines 322-326) early-returns when `g_HashGridScratch[slot].sampleCount >= HASHGRID_PER_FRAME_CAP`. The cap is enforced via a non-atomic pre-check, so a wavefront-sized overshoot (~32-64 contributions) is possible; that overshoot is harmless because (a) the worst-case scratch quantised sum stays at `(CAP + wavefront) × 100 × 1e3 ≪ uint32 max` (~1300x head-room from the post-TASK-208 firefly clamp), and (b) the EMA filter clamps the blended count to `HASHGRID_MAX_SAMPLE_COUNT` regardless.
- **Nature of divergence**: intentional. Bounds quantisation overflow on the write side as a defence-in-depth guard — Capsaicin can rely on its NEE/MIS upstream firefly suppression to keep per-cell contention bounded; we preserve that bound explicitly because our PT-primary write site has weaker upstream firefly handling (D13's clamp is the only line of defence).
- **Resolution**: DIVERGENT (intentional, scope-locked for phase-1.5). The cap is a named constant; if a future PT estimator gains stronger upstream firefly suppression / NEE re-weighting, the cap can be relaxed or removed.

## Reviewer-facing summary

Six of the recorded divergences are intentional phase-1 scope reductions, anchored in TASK-77.1's design-call resolution (2026-04-30) and TASK-77.1.1 / TASK-77.1.2 closure records. **D9 (the algorithmically load-bearing divergence — non-atomic radiance accumulation) is now FAITHFUL** as of TASK-208 (phase-1.5): InterlockedAdd into a per-frame scratch buffer is drained into a persistent EMA value buffer by `GPUPathTracerHashGridFilter.comp`, mirroring Capsaicin's `gi1.comp:2160-2217 UpdateTilesMain` shape. Phase-1.5 also lands power-of-2 cell-size quantisation (D3 form FAITHFUL).

D11/D12/D13 are new parameter-space divergences introduced by phase-1.5 — cell-size constant at 64 px, normal binning at 3 bits per axis, cache-side firefly clamp at 100 luma. All three are tuning choices for the PT-primary-hit usage shape; the scope-locked resolution is to keep them as named constants in the shader, with a future task to promote to CB if scene-tunable values are needed.

**TASK-208 AC #4 (≥5x stddev drop on at least one of {p50, p95, p99}, cache-on vs cache-off) was met at the initial phase-1.5 close (5.53x p50)** but the implementation surfaced a visible cell-boundary checkerboard at fixed camera that the temporal-only metric was structurally blind to (each cell was temporally stable; the spatial cell *boundaries* were the failure mode). The TASK-208 fix-up (2026-05-01) consciously trades AC #4 numerical headroom for visible-correctness: cellSizePx 64→16 (D11), kMaxCacheWeight = 0.7 composition ceiling (D16), tangent-plane multi-tap read (D15). - Cache-on (post-fix-up): p50 = 15.95, p95 = 41.51, p99 = 61.59, max = 123.07.
