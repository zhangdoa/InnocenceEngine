## Description

`GPUModelData` (becoming `RenderInstance` after TASK-253) is a god-struct
that conflates four different lifetimes and concerns. This task is the
**full decomposition** into the canonical GPU-driven rendering model.

### The current conflation

```
GPUModelData (160B) currently contains:
  - GEOMETRY (per unique mesh, static, shared across instances):
    m_VertexBufferAddress, m_IndexBufferAddress,
    m_VertexCount, m_IndexCount, m_VertexStride, m_IndexStride
  - INSTANCE (per visible object, per frame):
    m_MaterialIndex,
    m_BoundingBoxMin, m_BoundingBoxMax
  - DRAW ARGS (should be GPU-GENERATED, not CPU-authored):
    m_InstanceCount = 1, m_FirstInstance = 0
  - DEAD (write-only, never read by HLSL — removed in TASK-253):
    m_ShaderProgramIndex, m_RenderPassIndex, m_UUID, m_VisibilityMask, m_MeshUsage
```

A single struct holding **static-shared + per-frame-dynamic + GPU-generated +
dead** data is the structural reason fields silently rot in this struct
(the validator found three unwritten fields because nobody could tell what
was supposed to be filled).

### The decomposition (canonical GPU-driven rendering model)

Separate by **who owns it and how often it changes**, not by "stuff a draw
needs":

```cpp
// Per unique mesh. Uploaded once on residency. Indexed by meshID.
struct MeshGeometry {                  // was: 6 fields of GPUModelData
    uint64_t vertexBufferAddress, indexBufferAddress;
    uint32_t vertexCount, indexCount, vertexStride, indexStride;
};

// Per visible instance, per frame. The real "draw candidate."
struct RenderInstance {                // was: the dynamic fields
    uint32_t meshID;                   // -> index into the MeshGeometry table
    uint32_t materialID;               // -> index into the material table
    uint32_t transformID;              // -> index into the transform table
    Vec4     worldAabbMin, worldAabbMax;
};

// GPU-generated by opaqueGPUCulling.comp. Never CPU-authored.
struct IndirectDrawCommand { ... };    // D3D12_DRAW_INDEXED_ARGUMENTS, written by the cull pass
```

The culling shader already does
`IsInFrustum(aabb) -> BuildIndirectDrawCommand(...)` — it's *already* the
consumer that turns a `RenderInstance` into an `IndirectDrawCommand`. The
dataflow should match: instance in, draw-command out. Today the CPU
pre-fills `m_InstanceCount=1, m_FirstInstance=0` that the cull pass
should own.

### Why this is the correct model

From the GPU-driven rendering literature (Unreal's Nanite, Frostbite's
GI, AMD GPUOpen samples), this is the standard split. The benefits are
load-bearing, not aesthetic:

1. **Sharing falls out for free.** 100 instances of one mesh = 1
   `MeshGeometry` + 100 `RenderInstance`s, instead of 100 copies of
   the vertex-buffer address. Today the GPU has 100 copies of the
   address in a per-frame `StructuredBuffer`.
2. **The cull pass writes the draw command, not the CPU.** The CPU
   today pre-fills `m_InstanceCount = 1` to "lie" to the cull pass.
   Once the cull pass owns the draw command, it can also cull
   per-mesh vs per-instance (1 mesh in 1 draw vs 1 mesh in 100
   instances is the same thing under the new model).
3. **The functional-core / imperative-shell split becomes possible.**
   A `RenderInstance` has no optional fields. The producer becomes
   `RenderInstance::From(MeshRenderRecord)` with no conditionals.
   Domain resolution (mesh asset, world transform, material) moves
   to a residency-time `MeshGeometryService` and a per-frame
   `InstanceCollector` that explicitly decide: cull, or substitute
   a named default.
4. **Dead fields can't hide.** The current `m_ShaderProgramIndex`/
   `m_RenderPassIndex`/`m_UUID`/`m_VisibilityMask`/`m_MeshUsage` are
   all write-only and rotting. They exist because the struct was the
   catch-all for "stuff a draw needs." Decomposing the struct by
   lifetime forces every field to have a producer.
5. **C++/HLSL layout becomes a runtime, not a coincidence.** The
   fact that the C++ and HLSL `GPUModelData` layouts match at 160B
   is currently a manual contract. Once the struct is split, the
   `MeshGeometry` table is a one-time upload (rare change), the
   `RenderInstance` table is per-frame, and the `IndirectDrawCommand`
   buffer is GPU-written. The three have different uploaders, different
   states, different validators.

### Investigation hints

- The current `cbuffer`/`StructuredBuffer` line is in
  `Source/Shaders/HLSL/common/common.hlsl:530-558` and used by
  `opaqueGPUCulling.comp:13` and `opaqueGeometryProcessPass.frag:23`.
  The new structure is:
    - `StructuredBuffer<MeshGeometry> u_MeshGeometryBuffer` (SRV, read-only)
    - `StructuredBuffer<RenderInstance> u_RenderInstanceBuffer` (SRV, per-frame)
    - `RWByteAddressBuffer u_DrawCommandBuffer` (UAV, GPU-written)
- `RenderInstance` references `MeshGeometry` by `meshID`. The cull
  pass reads `RenderInstance[objectIndex].meshID` → `MeshGeometry[meshID]`.
- `DrawCallService` becomes the orchestrator of these uploads but
  doesn't itself build per-instance data. The `StageMeshGeometries`
  step is a one-time upload triggered by mesh-residency events (the
  same events `MeshResourceService` already fires).
- The C++ `MeshGeometry` struct should be derived from
  `GPUUploadable<MeshGeometry>` with the same EBO + static_assert
  pattern as the other CBs (TASK-249).

- **2026-06-22:** Closed the remaining AC1 + AC4 sub-bullets. AssetService owns a
  monotonic `s_MeshResidencyEpoch` bumped on each mesh Resident (MeshResourceService)
  / Released (ReleaseAssetsByLifespan) transition; DrawCallService rebuilds the
  MeshGeometry table (`StageMeshGeometries()` — locks the asset mutex + scans every
  mesh asset, the real per-frame cost) only when the epoch differs from its
  last-staged high-water mark (`m_LastStagedResidencyEpoch`, init UINT64_MAX so
  frame 0 stages). `UpdateDrawCalls()` removed; `Update()` orchestrates
  (stage-if-dirty → collect → uploads). `CollectVisibleInstances()` is now an
  imperative shell (resolve mesh/material/transform/meshID + cull-or-substitute)
  feeding three conditional-free pure producers — `ToRenderInstance` /
  `ToTransformConstantBuffer` / `ToMaterialConstantBuffer` — over a fully-resolved
  `ResolvedRenderRecord`. Two degenerate-case fixes fell out: a missing WorldTransform
  now substitutes identity (was a zero matrix that collapsed geometry); a missing
  material asset now zeroes attributes (was left poisoned, a latent validator trip).
  IMPORTANT: the MeshGeometry *upload* stays per-frame (to the current ring slot),
  NOT one-time. The buffer is multi-buffered (one mapped copy per swap-chain image,
  3 here); `Upload` only writes `m_MappedMemories[currentFrame]`, so a literal
  one-time upload populates one of three slots and the GPU reads empty geometry on
  2 of every 3 frames — this shipped briefly as SEVERE FLICKER (user-reported) and
  was fixed by reverting the upload to per-frame while keeping the staging gated.
  AC1's "one-time upload" is therefore read as "one-time table *rebuild* per
  residency"; the per-frame upload is a trivial ~480B memcpy, same discipline as
  RenderInstance/Transform/Material. Writing all slots at once is unsafe (other
  slots' frames may still be in GPU flight — the ring's whole purpose). Verified on
  the fixed build via the Audit preset (UnitTest, offscreen): instanceCount=56,
  validators silent (0 unwritten), 0 D3D12 errors, all 13 passes dumped (GBuffer
  non-black, values byte-identical to baseline), clean terminate; a temporary
  counter earlier proved StageMeshGeometries runs once per residency (epoch=15 →
  15 unique meshes shared across 56 instances) vs 35× under the old per-frame scan.
  No separate MeshGeometryService/InstanceCollector class needed — the epoch gate +
  shell/core split inside DrawCallService satisfies every AC. (The intermittent
  engine hang seen during verification is the pre-existing TASK-241, out of scope.)
